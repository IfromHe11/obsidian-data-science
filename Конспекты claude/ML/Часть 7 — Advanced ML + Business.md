# Раздел 26. Ensemble Methods — полная картина

Мы уже разбирали Bagging (Random Forest) и Boosting (Gradient Boosting) в Части 4. Дополним картину оставшимися видами ансамблирования.

## Bagging vs Boosting (напоминание и сравнение)

||Bagging|Boosting|
|---|---|---|
|Базовые модели|Обучаются независимо, параллельно|Обучаются последовательно, каждая исправляет ошибки предыдущих|
|Что снижает|Variance|Bias|
|Пример|Random Forest|Gradient Boosting, XGBoost, LightGBM, CatBoost|

## Voting (голосование)

**Идея:** обучить **несколько разных** моделей (например, Logistic Regression + Random Forest + SVM) на **одних и тех же** данных, и объединить их предсказания голосованием.

- **Hard voting** — каждая модель "голосует" за конкретный класс, побеждает класс большинства голосов.
- **Soft voting** — усредняются предсказанные **вероятности** классов от каждой модели, и итоговый класс выбирается по наибольшей усреднённой вероятности. Обычно даёт лучший результат, чем hard voting, так как учитывает уверенность каждой модели, а не только её "решение".

**Почему это работает:** если модели совершают **разные типы ошибок** (например, линейная модель ошибается на нелинейных участках, а дерево — на участках, где нужна экстраполяция), объединение их предсказаний может компенсировать индивидуальные слабости каждой отдельной модели.

## Stacking (стекинг)

**Идея:** вместо простого голосования/усреднения, обучается **дополнительная модель (мета-модель)**, которая учится **оптимально комбинировать** предсказания базовых моделей.

**Как это работает:**

1. Несколько разных базовых моделей (level-0 models) обучаются на исходных данных.
2. Их предсказания (например, вероятности классов) на кросс-валидационных фолдах становятся **новыми признаками**.
3. Мета-модель (level-1 model, часто простая — например, логистическая регрессия) обучается предсказывать целевую переменную, используя предсказания базовых моделей как входные признаки.

> **Важно.** Предсказания базовых моделей для обучения мета-модели должны быть получены через кросс-валидацию (out-of-fold predictions), а не просто предсказаниями на train, на котором эти базовые модели уже обучались — иначе мета-модель будет обучаться на переобученных, слишком оптимистичных предсказаниях базовых моделей, что также является формой data leakage (Часть 6).

## Blending

Упрощённый вариант stacking: вместо кросс-валидации для получения предсказаний базовых моделей, обучающая выборка один раз делится на две части — базовые модели обучаются на первой части, их предсказания на **второй** (holdout) части используются как признаки для обучения мета-модели. Проще в реализации, чем полноценный stacking, но использует данные менее эффективно (часть данных "тратится" только на генерацию признаков для мета-модели, а не участвует напрямую в обучении базовых моделей).

## Концептуальная разница

```
Bagging:   Модель A, Модель A, Модель A (разные подвыборки) → усреднение
Boosting:  Модель A → исправляет ошибки → Модель A → исправляет ошибки → ...
Voting:    Модель A + Модель B + Модель C (разные алгоритмы) → голосование/усреднение
Stacking:  Модель A + Модель B + Модель C → их предсказания → Мета-модель → финальный ответ
```

> **Запомни.** Bagging и Boosting комбинируют **один тип** базовой модели (обычно деревья) множеством разных способов. Voting и Stacking комбинируют **принципиально разные типы** моделей, используя разнообразие самих алгоритмов, а не только разнообразие обучающих выборок.

# Раздел 27. Как выбирать алгоритм — практический decision tree

```
У меня есть задача → какую ML-модель выбрать?

├── REGRESSION (предсказание числа)
│   ├── Нужна максимальная интерпретируемость → Linear Regression / Ridge / Lasso
│   ├── Умеренно сложная нелинейная зависимость, средний датасет → Random Forest
│   └── Нужна максимальная точность, есть время на тюнинг → Gradient Boosting / XGBoost / CatBoost
│
├── CLASSIFICATION (предсказание категории)
│   ├── Нужна интерпретируемость + калиброванные вероятности → Logistic Regression
│   ├── Текстовая классификация, мало данных → Naive Bayes
│   ├── Небольшой датасет, нелинейная граница, простота → KNN
│   ├── Нужна визуальная интерпретируемость для бизнеса → Decision Tree
│   ├── Надёжный baseline без сложного тюнинга → Random Forest
│   ├── Максимальная точность на табличных данных → Gradient Boosting / XGBoost / LightGBM
│   ├── Много категориальных признаков → CatBoost
│   └── Пространство высокой размерности, чёткая граница → SVM
│
├── CLUSTERING (группировка без меток)
│   ├── Кластеры примерно сферической формы, известно K → K-Means
│   ├── Кластеры сложной, произвольной формы + нужны выбросы → DBSCAN
│   └── Нужна иерархическая структура/дендрограмма, K неизвестно → Hierarchical Clustering
│
├── DIMENSIONALITY REDUCTION (снижение размерности)
│   └── Линейное сжатие признаков, борьба с мультиколлинеарностью → PCA
│
└── ANOMALY DETECTION (поиск аномалий)
    ├── Большие данные, много признаков → Isolation Forest
    ├── Обучение только на "нормальных" примерах → One-Class SVM
    └── Разная плотность в разных областях данных → Local Outlier Factor (LOF)
```

**Объяснение выбора для каждой ситуации:**

- **Начинайте с простого.** Почти всегда разумно начать с самого простого адекватного baseline (Linear/Logistic Regression) — это быстро, интерпретируемо, и даёт точку отсчёта для сравнения более сложных моделей. Если Gradient Boosting даёт лишь на 1% лучше accuracy, чем Logistic Regression, возможно, простота и скорость линейной модели того стоят.
- **Интерпретируемость важна?** Регулируемые отрасли (банки, медицина, страхование) часто требуют объяснимости решений — в таких случаях линейные модели или одиночные деревья предпочтительнее "чёрных ящиков", если только не используется дополнительная интерпретируемость через SHAP (Раздел 32).
- **Много категориальных признаков?** CatBoost сэкономит время на препроцессинге и часто даёт хороший результат без сложного тюнинга.
- **Очень большой датасет?** LightGBM для табличных данных, обычные Gradient Boosting/Random Forest могут быть медленнее на миллионах строк.
- **Нужна максимальная точность и есть время?** Gradient Boosting семейство почти всегда побеждает на табличных данных по сравнению с более простыми моделями, а стекинг нескольких сильных моделей может дать ещё небольшой прирост.

# Раздел 30. Реальные бизнес-примеры по типам задач

## Classification

- **Credit scoring:** Business Problem — оценить риск невозврата кредита → Data — история заявок → Features — доход, кредитная история, возраст, стаж → Model — Logistic Regression / XGBoost → Metric — ROC-AUC, Recall на классе дефолта → Business Impact — снижение доли невозвратов при сохранении объёма одобренных заявок.
- **Fraud detection:** Business Problem — обнаружить мошеннические транзакции → Data — история транзакций → Features — сумма, время, частота, геолокация → Model — Isolation Forest / XGBoost с балансировкой классов → Metric — Precision-Recall AUC, Recall → Business Impact — снижение финансовых потерь от мошенничества.
- **Churn prediction:** Business Problem — предсказать уход клиента → Data — история активности и платежей → Features — частота использования, длительность подписки, обращения в поддержку → Model — Random Forest / Gradient Boosting → Metric — Recall (не пропустить уходящих клиентов), F1 → Business Impact — таргетированное удержание через персональные предложения, рост LTV.
- **Spam detection:** Business Problem — фильтрация нежелательных писем → Data — размеченный корпус → Features — слова, метаданные отправителя → Model — Naive Bayes / Logistic Regression → Metric — Precision (не заблокировать легитимные письма) → Business Impact — снижение нагрузки на пользователей, доверие к почтовому сервису.

## Regression

- **House price prediction:** Business Problem — оценка справедливой стоимости недвижимости → Data — база сделок → Features — площадь, район, этаж, год постройки → Model — Ridge Regression / Gradient Boosting → Metric — RMSE, MAPE → Business Impact — автоматизация оценки объектов, ускорение сделок.
- **Demand forecasting:** Business Problem — спрогнозировать спрос на товар → Data — исторические продажи → Features — сезонность, промоакции, цена, погода → Model — Gradient Boosting с временными признаками → Metric — MAPE → Business Impact — оптимизация закупок и складских запасов, снижение излишков и дефицита.
- **Revenue prediction:** предсказание выручки для планирования бюджета на основе маркетинговых расходов, сезонности, числа активных клиентов.

## Clustering

- **Customer segmentation:** Business Problem — разбить клиентов на группы со схожим поведением → Data — история покупок и активности → Features — частота покупок, средний чек, категории товаров → Model — K-Means → Metric — Silhouette Score → Business Impact — персонализированные маркетинговые кампании для каждого сегмента.
- **Product segmentation:** группировка товаров по характеристикам продаж для оптимизации ассортимента и мерчандайзинга.

## Anomaly Detection

- **Fraud (детальнее):** транзакционные паттерны, сильно отклоняющиеся от типичного поведения клиента.
- **Equipment failure (предиктивное обслуживание):** Business Problem — предсказать поломку оборудования до того, как она произойдёт → Data — показания датчиков → Features — вибрация, температура, давление во времени → Model — Isolation Forest / LSTM (выходит за рамки классического ML) → Business Impact — снижение простоев производства, плановое обслуживание вместо аварийного ремонта.
- **Cybersecurity:** обнаружение аномального сетевого трафика, потенциально указывающего на кибератаку.

# Раздел 31. ML-метрика vs Business-метрика

## Ключевая идея

$ROC\text{-}AUC = 0.87$ — это хорошая **ML-метрика**, но она **ничего не говорит бизнесу напрямую** о деньгах, риске или клиентском опыте. Задача ML-инженера — уметь **переводить** качество модели на язык, понятный бизнесу: прибыль, издержки, уровень риска, удержание клиентов.

## Business metrics (примеры)

- **Profit / Revenue** — прямое влияние на выручку компании.
- **Cost** — стоимость ошибок модели (например, ложное одобрение кредита ненадёжному заёмщику).
- **Default rate** — доля невозвратов по кредитам.
- **Customer retention** — удержание клиентов.
- **Conversion** — доля пользователей, совершивших целевое действие.
- **Fraud losses** — прямые финансовые потери от необнаруженного мошенничества.

## Как переводить ML-качество в бизнес-ценность: пример

Рассмотрим модель кредитного скоринга с Precision = 0.8 и Recall = 0.6 для класса "дефолт" на тестовой выборке из 10 000 заявок, где реально 500 — дефолтные (5%).

Из confusion matrix: Recall = 0.6 означает, что модель находит $0.6 \times 500 = 300$ реальных дефолтов (TP), пропуская 200 (FN). Precision = 0.8 означает, что среди всех, кого модель пометила как "дефолт" ($300/0.8 = 375$ помеченных), 75 — ложные срабатывания (FP) — надёжные клиенты, которым будет **отказано в кредите незаслуженно**.

**Перевод в деньги:** если средний кредит — 500 000 ₽, и при дефолте банк теряет в среднем 70% суммы (350 000 ₽), то:

- Предотвращённые потери от найденных дефолтов: $300 \times 350,000 = 105,000,000$ ₽.
- Упущенная выручка от процентов по 75 ошибочно отклонённым надёжным заявкам (условно 50 000 ₽ прибыли с каждого одобренного кредита): $75 \times 50,000 = 3,750,000$ ₽.
- Прямые потери от 200 пропущенных дефолтов: $200 \times 350,000 = 70,000,000$ ₽ (это то, что модель **не** смогла предотвратить).

Такой расчёт показывает, что **порог классификации** (влияющий на баланс Precision/Recall) нужно выбирать не по абстрактному "максимизируем F1", а исходя из **реальной денежной цены** каждого типа ошибки — в данном случае, возможно, стоит сдвинуть порог в сторону более высокого Recall (даже за счёт Precision), так как цена пропущенного дефолта (FN) значительно выше цены упущенной прибыли от одного отклонённого хорошего клиента (FP).

> **Запомни.** Всегда старайтесь довести оценку модели до конкретных денег или другой понятной бизнесу единицы измерения — это резко повышает доверие стейкхолдеров к ML-проекту и помогает принимать решения о том, какой порог, какую модель и какие компромиссы выбрать.

# Раздел 32. Интерпретируемость ML

**Зачем бизнесу понимать, почему модель приняла решение:** регуляторные требования (банки обязаны объяснять причину отказа в кредите), доверие пользователей и стейкхолдеров, отладка модели (нахождение ошибок, предвзятости/bias в данных), обнаружение data leakage (если "слишком хороший" признак имеет аномально высокую важность — возможно, это утечка).

## Feature Importance

Уже разобрано в Части 4 для деревьев — общая оценка вклада каждого признака в качество модели в целом (глобальная интерпретируемость).

## Permutation Importance

Также разобрано в Части 4 — модельно-независимый метод оценки важности признаков через измерение падения качества при перемешивании значений признака.

## Partial Dependence Plot (PDP, график частичной зависимости)

Показывает, как **в среднем** меняется предсказание модели при изменении значения **одного конкретного признака**, при этом усредняя (или "замораживая") влияние всех остальных признаков. Например, PDP для признака "возраст" в модели кредитного скоринга покажет, как в среднем меняется предсказанная вероятность дефолта при разных значениях возраста, независимо от других характеристик заявителя.

**Ограничение:** PDP показывает **глобальную**, усреднённую картину — не объясняет предсказание для **конкретного** отдельного объекта, и может быть обманчивым при сильных взаимодействиях между признаками.

## SHAP (SHapley Additive exPlanations)

**Идея:** SHAP основан на концепции **Shapley values** из теории игр — способе "справедливо" распределить общий "выигрыш" (в данном случае, отклонение предсказания модели от среднего) между всеми "игроками" (признаками), учитывая все возможные комбинации порядка их "вступления в игру".

**Что даёт SHAP:**

- **Локальная интерпретируемость** — для **конкретного** объекта показывает, какой вклад (положительный или отрицательный) внёс **каждый** признак в итоговое предсказание относительно среднего предсказания по всей модели. Например: "заявке присвоена вероятность дефолта 0.72 (выше среднего 0.5 на 0.22); низкий доход добавил +0.15 к риску, короткая кредитная история добавила +0.10, но стабильное место работы снизило риск на -0.03".
- **Глобальная интерпретируемость** — усреднение SHAP values по всем объектам dataseта даёт общую картину важности признаков, сопоставимую с feature importance, но более теоретически обоснованную и последовательную.

**Почему SHAP предпочтительнее простого feature importance:** feature importance деревьев может быть смещена (bias) в сторону признаков с большим числом уникальных значений (Часть 4); SHAP математически гарантирует "справедливое" распределение вклада, устойчиво к таким искажениям, и, что особенно ценно, работает **на уровне отдельного объекта**, а не только в среднем по всему датасету — что критически важно, когда нужно объяснить решение конкретному клиенту, а не просто описать модель в целом.

```python
import shap
from sklearn.ensemble import GradientBoostingClassifier

model = GradientBoostingClassifier().fit(X_train, y_train)
explainer = shap.TreeExplainer(model)
shap_values = explainer.shap_values(X_test)

shap.summary_plot(shap_values, X_test)          # глобальная важность признаков
shap.force_plot(explainer.expected_value, shap_values[0], X_test.iloc[0])  # объяснение одного предсказания
```

# Раздел 33. ML Workflow — полный процесс работы ML-инженера

```
Business Problem
    ↓
Data Collection
    ↓
EDA (Exploratory Data Analysis)
    ↓
Data Cleaning
    ↓
Feature Engineering
    ↓
Train/Test Split
    ↓
Baseline
    ↓
Model Selection
    ↓
Cross Validation
    ↓
Hyperparameter Tuning
    ↓
Evaluation
    ↓
Interpretation
    ↓
Business Evaluation
    ↓
Deployment
    ↓
Monitoring
```

|Этап|Что делать|Зачем|Частые ошибки|Инструменты|
|---|---|---|---|---|
|**Business Problem**|Чётко сформулировать бизнес-вопрос и как ML-решение будет использоваться|Без ясной цели легко построить точную, но бесполезную модель|Прыгать сразу к моделированию без понимания цели бизнеса|Обсуждения со стейкхолдерами|
|**Data Collection**|Собрать данные из нужных источников (БД, API, логи)|Качество данных определяет потолок качества модели|Собирать данные с обратной датой (не соответствующие моменту принятия решения в реальности)|SQL, API, Airflow|
|**EDA**|Изучить распределения, пропуски, выбросы, корреляции|Понять структуру данных до моделирования, выявить проблемы заранее|Пропустить EDA и сразу обучать модель "вслепую"|Pandas, Matplotlib, Seaborn|
|**Data Cleaning**|Обработать пропуски, дубликаты, аномальные значения|"Мусор на входе — мусор на выходе"|Заполнять пропуски без понимания причины их появления|Pandas|
|**Feature Engineering**|Создать/преобразовать признаки (Раздел 22)|Хорошие признаки часто важнее выбора алгоритма|Использовать признаки, недоступные на момент реального предсказания (см. data leakage)|Pandas, feature-engine, category_encoders|
|**Train/Test Split**|Разделить данные, зафиксировать test как "неприкасаемый"|Честная оценка на новых данных|Смотреть на test до финальной оценки, подгоняя модель под него|sklearn.model_selection|
|**Baseline**|Обучить простую модель (например, Logistic Regression, среднее значение)|Точка отсчёта — без неё непонятно, действительно ли сложная модель нужна|Сразу переходить к сложным моделям без baseline|sklearn|
|**Model Selection**|Попробовать несколько подходящих алгоритмов (Раздел 27)|Разные алгоритмы подходят разным типам данных|Использовать только один "любимый" алгоритм без сравнения|sklearn, XGBoost, LightGBM, CatBoost|
|**Cross Validation**|Оценить модели устойчиво, через несколько фолдов (Часть 6)|Одно разбиение может дать случайную, нерепрезентативную оценку|Использовать обычный K-Fold для временных рядов|sklearn.model_selection|
|**Hyperparameter Tuning**|Подобрать оптимальные гиперпараметры (Часть 6)|Существенно улучшает качество по сравнению с дефолтными настройками|Тюнить на test вместо validation (переобучение под test)|Optuna, GridSearchCV|
|**Evaluation**|Оценить финальную модель нужными метриками (Часть 6)|Выбор метрики должен отражать реальную бизнес-цель|Оптимизировать не ту метрику, которая реально важна бизнесу|sklearn.metrics|
|**Interpretation**|Понять, почему модель принимает такие решения (Раздел 32)|Доверие, отладка, соответствие регуляторным требованиям|Игнорировать интерпретируемость "чёрного ящика" до продакшена|SHAP, PDP|
|**Business Evaluation**|Перевести ML-метрики в бизнес-ценность (Раздел 31)|ML-метрика сама по себе не убеждает бизнес|Останавливаться на ROC-AUC, не считая деньги/эффект|Business-аналитика, A/B тесты|
|**Deployment**|Развернуть модель в продакшене (API, batch-джобы)|Модель бесполезна, пока не используется в реальном процессе|Игнорировать различия между офлайн- и онлайн-средой (skew)|Docker, FastAPI, MLflow, облачные сервисы|
|**Monitoring**|Отслеживать качество модели во времени|Данные и поведение пользователей меняются (**data drift**), модель "стареет"|Развернуть модель и забыть про неё навсегда|Evidently, Prometheus, дашборды|

> **Важно.** ML-проект — это **не** линейный процесс "один раз прошли и забыли". EDA может выявить проблему, требующую вернуться к сбору данных; мониторинг в продакшене может показать деградацию качества (data drift — когда распределение входных данных со временем меняется и отличается от того, на чём модель обучалась), требующую переобучения модели на новых данных. Реальный ML Workflow — это **цикл**, а не прямая линия.
