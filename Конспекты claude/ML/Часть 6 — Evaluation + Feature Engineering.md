# Раздел 19. Model Evaluation

## Regression Metrics

### MAE (Mean Absolute Error)

$$MAE = \frac{1}{n}\sum_{i=1}^{n}|y_i - \hat{y}_i|$$

**Смысл:** средняя абсолютная ошибка в тех же единицах, что и целевая переменная (например, "в среднем модель ошибается на 350 тыс. ₽ при прогнозе цены квартиры").

**Плюсы:** легко интерпретируется; устойчива к выбросам (в отличие от MSE, не возводит ошибку в квадрат). **Минусы:** не дифференцируема в нуле (менее удобна для градиентной оптимизации напрямую); одинаково штрафует ошибки любого размера — не выделяет "особо плохие" промахи. **Когда использовать:** когда важно понятное, интерпретируемое среднее отклонение, и вы не хотите, чтобы редкие крупные ошибки чрезмерно доминировали в оценке.

### MSE (Mean Squared Error)

Уже подробно разобрана в Части 2: $MSE = \frac{1}{n}\sum(y_i-\hat{y}_i)^2$.

**Плюсы:** дифференцируема, удобна для оптимизации; сильно штрафует крупные ошибки. **Минусы:** единицы измерения — это квадрат единиц целевой переменной (например, "квадратные миллионы рублей"), что плохо интерпретируется напрямую; чувствительна к выбросам. **Когда использовать:** как функция потерь при обучении; как метрика — когда крупные ошибки действительно особенно нежелательны для бизнеса.

### RMSE (Root Mean Squared Error)

$$RMSE = \sqrt{MSE} = \sqrt{\frac{1}{n}\sum_{i=1}^n(y_i-\hat{y}_i)^2}$$

**Смысл:** тот же принцип, что и MSE (сильный штраф за крупные ошибки), но после извлечения корня метрика возвращается в исходные единицы измерения целевой переменной — поэтому RMSE **гораздо более интерпретируема**, чем MSE, и на практике используется как основная метрика для отчётности гораздо чаще, чем "сырая" MSE.

**Плюсы:** интерпретируема (единицы совпадают с $y$), чувствительна к крупным ошибкам (что часто и нужно бизнесу). **Минусы:** те же проблемы с чувствительностью к выбросам, что и у MSE. **Когда использовать:** самая частая метрика регрессии "по умолчанию" на практике.

### R² (коэффициент детерминации)

$$R^2 = 1 - \frac{\sum_{i=1}^n(y_i-\hat{y}_i)^2}{\sum_{i=1}^n(y_i-\bar{y})^2}$$

**Разбор:** числитель — сумма квадратов ошибок модели (SSE — sum of squared errors); знаменатель — сумма квадратов отклонений от простого среднего (то есть ошибка "наивной" модели, которая всегда предсказывает $\bar{y}$). $R^2$ показывает, **какую долю дисперсии целевой переменной объясняет модель** по сравнению с этой наивной моделью.

- $R^2 = 1$ — модель идеально объясняет все данные.
- $R^2 = 0$ — модель не лучше, чем просто предсказание среднего значения.
- $R^2 < 0$ — модель **хуже**, чем наивное предсказание среднего (случается на новых, "плохих" данных при переобучении).

**Плюсы:** безразмерная величина, легко сравнивать между разными задачами/датасетами. **Минусы:** может искусственно расти при добавлении **любых** новых признаков, даже бесполезных (для этого существует **Adjusted R²**, штрафующий за число признаков); не показывает абсолютную величину ошибки в понятных единицах. **Когда использовать:** для быстрой оценки "насколько хороша модель по сравнению с тривиальным baseline"; часто приводится вместе с RMSE, а не вместо неё.

### MAPE (Mean Absolute Percentage Error)

MAPE = \frac{100%}{n}\sum_{i=1}^n\left|\frac{y_i - \hat{y}_i}{y_i}\right|$$

**Смысл:** средняя ошибка в **процентах** от истинного значения — удобно, когда нужно сравнивать точность модели на объектах разного масштаба (например, прогноз продаж для маленького магазина и для крупной сети).

**Плюсы:** интерпретируется в процентах — понятна нетехническим людям ("модель ошибается в среднем на 8%"). **Минусы:** **неопределена**, если $y_i = 0$ (деление на ноль); несимметрична — сильнее штрафует занижение прогноза, чем завышение (при одинаковой абсолютной ошибке). **Когда использовать:** прогнозирование спроса/продаж, где относительная ошибка важнее абсолютной, и целевая переменная не бывает равна (или близка к) нулю.

## Classification Metrics

### Confusion Matrix (матрица ошибок)

Таблица, показывающая, как предсказания модели соотносятся с истинными классами (для бинарной классификации):

||Predicted: Positive|Predicted: Negative|
|---|---|---|
|**Actual: Positive**|TP (True Positive)|FN (False Negative)|
|**Actual: Negative**|FP (False Positive)|TN (True Negative)|

- **TP (True Positive)** — модель верно предсказала положительный класс.
- **TN (True Negative)** — модель верно предсказала отрицательный класс.
- **FP (False Positive)** — модель ошибочно предсказала положительный класс ("ложная тревога", Type I error).
- **FN (False Negative)** — модель ошибочно предсказала отрицательный класс ("пропуск", Type II error).

### Accuracy

$$Accuracy = \frac{TP+TN}{TP+TN+FP+FN}$$

Доля правильных предсказаний среди всех. **Простая, но опасная метрика при несбалансированных классах.**

> **Важно. Где Accuracy вводит в заблуждение.** Представим датасет с 10 000 транзакций, из которых лишь 100 (1%) — мошеннические. Модель, которая **всегда** предсказывает "не мошенничество", получит accuracy = 99%, выглядя почти идеально — но она абсолютно бесполезна, так как не поймает ни одного реального случая мошенничества. В таких задачах (fraud detection, редкие заболевания, дефекты оборудования) accuracy почти никогда не должна быть главной метрикой.

### Precision (точность)

$$Precision = \frac{TP}{TP+FP}$$

**Смысл:** из всех объектов, которые модель пометила как "положительные", какая доля действительно положительна? Отвечает на вопрос: "насколько можно доверять положительным предсказаниям модели?"

**Когда важнее Recall:** когда цена **ложного срабатывания (FP)** высока. Пример: спам-фильтр — если важное письмо ошибочно попадёт в спам (FP), пользователь может пропустить критически важную информацию; лучше пропустить немного спама, чем заблокировать легитимные письма.

### Recall (полнота, он же Sensitivity, True Positive Rate)

$$Recall = \frac{TP}{TP+FN}$$

**Смысл:** из всех **реально** положительных объектов, какую долю модель смогла найти? Отвечает на вопрос: "какую часть реальных случаев модель не пропустила?"

**Когда важнее Precision:** когда цена **пропуска (FN)** высока. Пример: диагностика онкологического заболевания — пропустить реального больного (FN) значительно опаснее, чем отправить здорового человека на дополнительное обследование (FP).

> **Типичная ошибка новичка.** Пытаться одновременно максимизировать и Precision, и Recall без понимания их фундаментального компромисса (trade-off): повышение порога классификации обычно увеличивает Precision, но снижает Recall, и наоборот. Нужно осознанно выбирать баланс, исходя из бизнес-цены каждого типа ошибки.

### F1-score

$$F1 = 2 \cdot \frac{Precision \cdot Recall}{Precision + Recall}$$

**Смысл:** гармоническое среднее Precision и Recall — в отличие от простого среднего, гармоническое среднее "штрафует" сильнее, если хотя бы одна из двух метрик низкая (F1 близок к нулю, если хотя бы одна из Precision/Recall близка к нулю). Удобная единая метрика, когда важен баланс между Precision и Recall, а не только одна из них.

### ROC-AUC

**ROC curve (Receiver Operating Characteristic)** — график, показывающий зависимость **True Positive Rate (Recall)** от **False Positive Rate** ($FPR = \frac{FP}{FP+TN}$) при **всех возможных порогах классификации** (не только 0.5).

**AUC (Area Under Curve)** — площадь под этой кривой, от 0 до 1:

- $AUC = 1$ — идеальный классификатор, полностью разделяющий классы при каком-то пороге.
- $AUC = 0.5$ — модель не лучше случайного угадывания.
- $AUC = 0$ — модель систематически "переворачивает" предсказания (что тоже можно использовать, инвертировав предсказания).

**Смысл ROC-AUC:** вероятность того, что модель присвоит случайно выбранному положительному объекту более высокую вероятность класса 1, чем случайно выбранному отрицательному объекту. Метрика **не зависит от выбора конкретного порога классификации** — оценивает качество ранжирования объектов моделью в целом.

### PR-AUC (Precision-Recall AUC)

Аналогично ROC-AUC, но строится кривая зависимости Precision от Recall при разных порогах, и считается площадь под ней.

> **Важно.** При **сильно несбалансированных классах** (мало положительных примеров) ROC-AUC может давать излишне оптимистичную картину, так как FPR слабо меняется при большом числе TN (истинно отрицательных объектов много). **PR-AUC более информативна в таких случаях**, так как она полностью фокусируется на поведении модели именно в отношении положительного (обычно редкого и более важного) класса.

### LogLoss

Уже разобран в Части 3 — оценивает не только правильность класса, но и **уверенность** модели в предсказании, сильно штрафуя уверенные, но неверные предсказания.

### Сводная таблица

|Метрика|Формула (кратко)|Плюсы|Минусы|Когда использовать|
|---|---|---|---|---|
|Accuracy|(TP+TN)/всего|Просто, интуитивно|Вводит в заблуждение при дисбалансе классов|Сбалансированные классы|
|Precision|TP/(TP+FP)|Показывает "чистоту" положительных предсказаний|Не учитывает пропущенные (FN)|Дорого ошибиться "ложной тревогой"|
|Recall|TP/(TP+FN)|Показывает полноту обнаружения|Не учитывает лишние срабатывания (FP)|Дорого пропустить реальный случай|
|F1|Гармоническое среднее P и R|Единая метрика при дисбалансе интересов|Скрывает, какая из двух метрик "хромает"|Нужен баланс Precision/Recall|
|ROC-AUC|Площадь под ROC-кривой|Не зависит от порога|Оптимистична при сильном дисбалансе классов|Общая оценка ранжирующей способности|
|PR-AUC|Площадь под PR-кривой|Точнее ROC-AUC при дисбалансе|Менее привычна, сложнее интерпретировать "на глаз"|Сильный дисбаланс классов, важен положительный класс|
|LogLoss|$-\frac{1}{n}\sum[y\ln\hat p+(1-y)\ln(1-\hat p)]$|Учитывает уверенность модели|Менее интуитивна для бизнеса|Когда важна калибровка вероятностей|

# Раздел 20. Cross-Validation

## Почему нельзя просто один раз разделить датасет

Если случайно разбить данные один раз на train/test, оценка качества модели будет зависеть от того, **какие именно** объекты случайно попали в тестовую выборку — при "удачном" разбиении оценка может оказаться завышенной, при "неудачном" — заниженной. Это особенно критично на небольших датасетах, где случайность разбиения сильно влияет на результат. Cross-validation даёт **более надёжную, усреднённую** оценку качества модели, используя данные эффективнее.

## K-Fold Cross-Validation

Датасет случайно делится на $K$ примерно равных частей (folds). Модель обучается $K$ раз: каждый раз одна часть используется как валидационная выборка, а оставшиеся $K-1$ частей — как обучающая. Итоговая оценка качества — среднее (и стандартное отклонение) метрики по всем $K$ запускам.

**Преимущество:** каждый объект датасета побывал и в обучающей, и в валидационной выборке — оценка использует все данные и гораздо устойчивее к случайности одного разбиения.

## Stratified K-Fold

Обычное случайное разбиение на K-Fold может случайно дать фолды с сильно разным соотношением классов (особенно критично при несбалансированных классах — например, в одном фолде может оказаться 0 положительных примеров). **Stratified K-Fold** гарантирует, что в каждом фолде сохраняется **то же соотношение классов**, что и в исходном датасете.

> **Важно.** Для задач классификации, особенно с несбалансированными классами, Stratified K-Fold должен быть выбором **по умолчанию**, а не обычный K-Fold.

## Leave-One-Out (LOO)

Частный случай K-Fold, где $K = n$ (число объектов) — то есть каждый раз ровно один объект используется для валидации, а все остальные — для обучения. Даёт максимально возможное использование данных для обучения на каждой итерации, но требует обучить модель $n$ раз — вычислительно очень дорого на больших датасетах, поэтому используется в основном на очень маленьких датасетах.

## Time Series Split

Для данных с временной структурой (временные ряды) **нельзя** использовать обычный случайный K-Fold — это привело бы к тому, что модель обучалась бы на "будущих" данных и валидировалась на "прошлых", что не соответствует реальному сценарию использования модели (в реальности мы всегда предсказываем будущее по прошлому) и приводит к **утечке данных (data leakage)**. Time Series Split сохраняет временной порядок: обучающая выборка всегда состоит только из данных, предшествующих валидационной выборке по времени, и с каждым следующим фолдом окно обучения "сдвигается вперёд" во времени.

> **Типичная ошибка новичка.** Применять обычный случайный K-Fold к временным рядам (прогноз продаж, финансовые данные) — это даёт завышенную, нереалистичную оценку качества модели, так как модель "подглядывает" в будущее при обучении.

# Раздел 21. Overfitting / Underfitting и Bias-Variance Tradeoff

## Overfitting (переобучение)

Модель слишком точно подстраивается под **обучающие** данные, включая случайный шум и особенности конкретной выборки, из-за чего плохо обобщается на новые данные. Признак: высокое качество на train, заметно более низкое качество на test/validation.

## Underfitting (недообучение)

Модель слишком проста, чтобы уловить даже основную закономерность в данных. Признак: низкое качество **и** на train, **и** на test — модель "не старается" достаточно даже на знакомых данных.

## Bias (смещение)

Систематическая ошибка модели из-за чрезмерного упрощения реальной зависимости. Высокий bias — модель делает сильные, часто неверные предположения о форме зависимости (например, пытается провести прямую линию через явно нелинейные данные) — типичный признак underfitting.

## Variance (дисперсия, в контексте модели)

Насколько сильно предсказания модели меняются при обучении на разных выборках данных из той же генеральной совокупности. Высокий variance — модель слишком чувствительна к конкретной обучающей выборке, "запоминает" её особенности — типичный признак overfitting.

## Bias-Variance Tradeoff

$$\text{Total Error} \approx \text{Bias}^2 + \text{Variance} + \text{Irreducible Error}$$

**Разбор:** общая ошибка модели на новых данных раскладывается на три компонента: $Bias^2$ — ошибка от неверных предположений модели; $Variance$ — ошибка от чрезмерной чувствительности к конкретной обучающей выборке; **Irreducible error (неустранимая ошибка)** — шум, присущий самим данным, который не может устранить никакая модель.

**Ключевая проблема:** Bias и Variance обычно находятся в противофазе — **уменьшение одного увеличивает другое**. Простая модель (например, линейная регрессия) имеет высокий bias, но низкий variance. Очень сложная модель (например, глубокое дерево решений без ограничений) имеет низкий bias, но высокий variance. Задача ML-инженера — найти "золотую середину", минимизирующую **суммарную** ошибку.

## Связь: Model Complexity → Bias/Variance → Generalization

```
Простая модель          Оптимальная сложность         Сложная модель
(underfitting)                                          (overfitting)
    ↓                            ↓                            ↓
Высокий Bias              Баланс Bias/Variance          Низкий Bias
Низкий Variance                                          Высокий Variance
    ↓                            ↓                            ↓
Плохо на train              Хорошо на train              Отлично на train
Плохо на test              Хорошо на test               Плохо на test
```

Эта зависимость обычно визуализируется как U-образная кривая ошибки на валидации в зависимости от сложности модели: ошибка сначала падает по мере роста сложности (уменьшается bias), затем начинает расти (растёт variance) — минимум этой кривой и есть оптимальная сложность модели.

> **Запомни.** Практические инструменты против overfitting (высокий variance): регуляризация, упрощение модели, больше данных, ансамблирование (Bagging), ранняя остановка, кросс-валидация для честного подбора сложности.
> 
> Практические инструменты против underfitting (высокий bias): усложнение модели, добавление новых информативных признаков, уменьшение силы регуляризации, использование более гибких алгоритмов (например, переход от линейной модели к Gradient Boosting).

# Раздел 22. Feature Engineering

## Numerical features (числовые признаки)

Требуют обработки: пропущенные значения, выбросы, масштаб.

**Missing values (пропущенные значения):** заполняются средним/медианой (для числовых), модой (для категориальных), или предсказываются отдельной моделью; либо создаётся отдельный бинарный признак "было ли значение пропущено" — иногда сам факт пропуска несёт информацию (например, "доход не указан" может коррелировать с определённой группой клиентов).

**Outliers (выбросы):** обрабатываются через отсечение (clipping) по квантилям, логарифмирование, или удаление явно ошибочных значений (например, возраст = 200 лет — техническая ошибка ввода данных).

## Scaling: normalization vs standardization

**Standardization (стандартизация, z-score normalization):**

$$x_{scaled} = \frac{x - \mu}{\sigma}$$

Приводит признак к среднему 0 и стандартному отклонению 1. Не ограничивает значения конкретным диапазоном.

**Normalization (нормализация, min-max scaling):**

$$x_{scaled} = \frac{x - x_{min}}{x_{max}-x_{min}}$$

Приводит значения строго в диапазон $[0, 1]$. Более чувствительна к выбросам (один экстремальный выброс сильно "сжимает" остальные значения к узкому диапазону).

### Каким моделям scaling критичен, а каким — нет

|Модель|Нужен ли scaling|Почему|
|---|---|---|
|Linear/Logistic Regression (с регуляризацией)|Да, критично|Регуляризация штрафует коэффициенты — признаки с большим масштабом получат несправедливо малые коэффициенты и наоборот|
|KNN, K-Means, SVM|Да, критично|Основаны на вычислении расстояний между объектами|
|PCA|Да, критично|Основан на дисперсии признаков, которая напрямую зависит от масштаба|
|Neural Networks|Да, критично|Ускоряет и стабилизирует сходимость Gradient Descent|
|Decision Tree, Random Forest, Gradient Boosting|Нет, не требуется|Разбиения основаны на пороговых сравнениях ($x \leq threshold$), которые не зависят от масштаба признака|
|Naive Bayes|Обычно нет|Работает с вероятностными распределениями каждого признака независимо|

> **Запомни.** Простое правило: если алгоритм в своей основе использует **расстояния** или **градиентную оптимизацию с регуляризацией**, scaling нужен. Если алгоритм основан на **древовидных разбиениях** по порогу, scaling не нужен.

## Log transformation (логарифмирование)

Применяется к признакам с сильно скошенным (правостороннее скошенное, right-skewed) распределением — типично для дохода, цены, числа посещений сайта и т.д. Логарифмирование "сжимает" большие значения сильнее, чем маленькие, приближая распределение к более симметричному, что часто улучшает работу линейных моделей и снижает влияние экстремальных выбросов.

## Polynomial и interaction features

**Polynomial features (полиномиальные признаки):** добавление степеней исходных признаков ($x^2$, $x^3$...) позволяет линейным моделям улавливать нелинейные зависимости — по сути, мы "обманываем" линейную модель, подавая ей уже нелинейно преобразованные входные данные, относительно которых зависимость снова становится линейной.

**Interaction features (признаки взаимодействия):** произведения двух и более признаков ($x_1 \cdot x_2$), позволяющие модели уловить эффекты, когда влияние одного признака зависит от значения другого (например, эффект скидки может быть значим только в сочетании с высоким доходом клиента).

## Кодирование категориальных признаков

**One-hot encoding:** каждая категория превращается в отдельный бинарный столбец (1, если объект принадлежит этой категории, иначе 0). Подходит для признаков без естественного порядка (например, "город") с небольшим числом уникальных категорий.

**Ordinal encoding:** категориям присваиваются целые числа согласно их естественному порядку (например, "низкий" = 0, "средний" = 1, "высокий" = 2). Подходит только для признаков, где порядок содержательно осмыслен.

**Target encoding:** каждая категория заменяется статистикой целевой переменной для этой категории (например, средним значением $y$ среди объектов с этой категорией). Эффективно работает при большом числе уникальных категорий (где one-hot создал бы слишком много новых столбцов), но требует аккуратности из-за риска data leakage (см. Раздел 24) — обычно применяется с техниками сглаживания и кросс-валидацией внутри самого кодирования.

> **Типичная ошибка новичка.** Применять one-hot encoding к категориальному признаку с сотнями уникальных значений (например, "почтовый индекс") — создаёт сотни новых разреженных столбцов, резко увеличивая размерность и риск переобучения. В таких случаях лучше target encoding, группировка редких категорий, или использование моделей, нативно работающих с категориями (CatBoost, Часть 4).

# Раздел 23. Feature Selection

**Зачем нужен отбор признаков:** уменьшение переобучения, ускорение обучения и предсказания, улучшение интерпретируемости, удаление шумных/нерелевантных признаков.

## Filter methods (фильтрующие методы)

Оценивают полезность каждого признака **независимо от модели**, на основе статистических критериев:

- **Correlation** — отбрасывание признаков с очень низкой корреляцией с целевой переменной (для регрессии) или сильно коррелирующих друг с другом (мультиколлинеарность).
- **Mutual information (взаимная информация)** — обобщение корреляции, способное улавливать и **нелинейные** зависимости между признаком и целью.

**Плюсы:** очень быстрые, не зависят от конкретной модели. **Минусы:** не учитывают взаимодействия между признаками и специфику конкретного алгоритма.

## Wrapper methods (обёрточные методы)

Оценивают полезность подмножества признаков, **реально обучая модель** на разных наборах признаков и сравнивая качество.

**RFE (Recursive Feature Elimination):** начинает со всех признаков, итеративно обучает модель, удаляет наименее важный признак (по весу коэффициента или feature importance), повторяет процесс, пока не останется нужное число признаков.

**Плюсы:** учитывает реальное поведение конкретной модели. **Минусы:** вычислительно значительно дороже filter methods (нужно многократно переобучать модель).

## Embedded methods (встроенные методы)

Отбор признаков происходит **как часть процесса обучения** самой модели, без отдельного дополнительного этапа:

- **L1 regularization (Lasso)** — как разобрано в Части 2, автоматически обнуляет коэффициенты незначимых признаков прямо в процессе обучения.
- **Tree-based importance** — feature importance из Random Forest/Gradient Boosting (Часть 4) естественным образом ранжирует признаки по значимости как побочный продукт обучения.

**Плюсы:** эффективны по времени (отбор происходит "бесплатно", вместе с обучением). **Минусы:** привязаны к конкретному типу модели, могут не переноситься на другие алгоритмы.

# Раздел 24. ML Pipelines

## Зачем нужны Pipeline

Pipeline объединяет все шаги обработки данных и обучения модели в единый, воспроизводимый объект. Это не просто вопрос удобства кода — это критически важный инструмент для **предотвращения data leakage**.

```
Data
  ↓
Train/Test Split
  ↓
Preprocessing (масштабирование, кодирование)
  ↓
Feature Engineering
  ↓
Model
  ↓
Cross-validation
  ↓
Hyperparameter tuning
  ↓
Evaluation
```

## Data Leakage (утечка данных)

**Проблема:** если препроцессинг (например, стандартизация, заполнение пропусков средним, отбор признаков) выполняется **до** разделения на train/test и **на всём датасете сразу**, то статистики, посчитанные для трансформации (среднее, дисперсия, whatever), "просачиваются" из тестовых данных в обучающий процесс — модель косвенно получает информацию о тестовой выборке ещё до того, как должна была её увидеть. Это приводит к **завышенной, нереалистичной оценке качества** модели, которая не подтвердится в реальном продакшене на действительно новых данных.

### Пример неправильного pipeline

```python
# НЕПРАВИЛЬНО: масштабирование по всем данным до разделения
from sklearn.preprocessing import StandardScaler
from sklearn.model_selection import train_test_split

scaler = StandardScaler()
X_scaled = scaler.fit_transform(X)   # scaler "увидел" ВСЕ данные, включая будущий test
X_train, X_test, y_train, y_test = train_test_split(X_scaled, y)
# Среднее и дисперсия для стандартизации уже включают информацию из test - это утечка!
```

### Пример правильного pipeline

```python
# ПРАВИЛЬНО: сначала split, потом fit scaler ТОЛЬКО на train
from sklearn.preprocessing import StandardScaler
from sklearn.model_selection import train_test_split
from sklearn.pipeline import Pipeline
from sklearn.linear_model import LogisticRegression

X_train, X_test, y_train, y_test = train_test_split(X, y, random_state=42)

pipeline = Pipeline([
    ("scaler", StandardScaler()),          # fit только на train внутри pipeline
    ("model", LogisticRegression())
])

pipeline.fit(X_train, y_train)   # scaler.fit_transform() вызывается только на X_train
                                   # для X_test автоматически вызывается только .transform()
                                   # (используя статистики, посчитанные на train)
print(pipeline.score(X_test, y_test))
```

**Ключевое отличие:** объект `Pipeline` гарантирует, что каждый шаг предобработки, требующий "обучения" (fit) — вычисления среднего, дисперсии, статистик кодирования и т.д., — обучается **только на train**, а к test применяется только `.transform()` с уже зафиксированными на train статистиками. Это же правило распространяется и на кросс-валидацию: препроцессинг должен пересчитываться заново внутри **каждого фолда**, а не один раз на всём датасете — иначе даже кросс-валидация даст завышенную оценку.

> **Важно.** Data leakage — одна из самых частых и коварных ошибок в ML, потому что модель с утечкой данных показывает **отличные** метрики на валидации, но катастрофически проваливается в продакшене на реальных новых данных. Всегда стройте pipeline так, чтобы все статистики препроцессинга вычислялись строго на обучающих данных.

# Раздел 25. Hyperparameter Optimization

## Grid Search

Перебирает **все возможные комбинации** заданных значений гиперпараметров из заранее определённой сетки (grid) и выбирает комбинацию с лучшим качеством на кросс-валидации.

**Плюсы:** гарантированно находит лучшую комбинацию **в пределах заданной сетки**; прост для понимания. **Минусы:** вычислительная сложность растёт экспоненциально с числом гиперпараметров ("проклятие размерности" сетки) — быстро становится непрактичным при более чем 3-4 гиперпараметрах.

## Random Search

Вместо перебора всех комбинаций, случайным образом выбирает заданное число комбинаций гиперпараметров из указанных диапазонов/распределений.

**Плюсы:** часто находит сопоставимое по качеству решение значительно быстрее Grid Search, особенно когда лишь немногие гиперпараметры реально сильно влияют на качество (эмпирически доказанный факт — Random Search эффективно "исследует" пространство более важных гиперпараметров, не тратя время на полный перебор менее важных). **Минусы:** не гарантирует нахождение оптимума даже в пределах заданных диапазонов — результат зависит от случайности и числа попыток.

## Bayesian Optimization

Строит вероятностную модель (обычно Gaussian Process) зависимости качества от гиперпараметров **по уже опробованным точкам**, и **умно** выбирает следующую комбинацию гиперпараметров для проверки — балансируя между "исследованием" новых, неопробованных областей пространства гиперпараметров (exploration) и "эксплуатацией" уже найденных многообещающих областей (exploitation).

**Плюсы:** значительно эффективнее (требует меньше итераций для нахождения хорошего решения) по сравнению с Grid/Random Search, особенно когда одна итерация обучения модели вычислительно дорога. **Минусы:** сложнее в реализации "с нуля"; сама оптимизация вносит дополнительные накладные расходы (не имеет смысла для очень быстро обучающихся моделей, где проще перебрать много комбинаций напрямую).

## Optuna

Популярная современная библиотека для гиперпараметрической оптимизации, реализующая байесовскую оптимизацию (и другие алгоритмы) с удобным API, поддержкой pruning (досрочной остановки неперспективных запусков) и визуализацией результатов поиска.

```python
import optuna
from sklearn.model_selection import cross_val_score
from sklearn.ensemble import RandomForestClassifier

def objective(trial):
    n_estimators = trial.suggest_int("n_estimators", 50, 300)
    max_depth = trial.suggest_int("max_depth", 3, 15)
    model = RandomForestClassifier(n_estimators=n_estimators, max_depth=max_depth, random_state=42)
    score = cross_val_score(model, X_train, y_train, cv=5, scoring="roc_auc").mean()
    return score

study = optuna.create_study(direction="maximize")
study.optimize(objective, n_trials=50)
print(study.best_params)
```

## Когда какой подход использовать

|Метод|Когда использовать|
|---|---|
|Grid Search|Мало гиперпараметров (1-3), небольшие, дискретные диапазоны значений, важна гарантия полного перебора|
|Random Search|Больше гиперпараметров, ограничено время/вычислительные ресурсы, нужен разумный результат быстро|
|Bayesian Optimization / Optuna|Дорогое обучение каждой модели (например, крупные Gradient Boosting или нейросети), нужно максимально эффективно использовать ограниченный бюджет попыток|
